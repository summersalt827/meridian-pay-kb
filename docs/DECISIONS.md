# 关键设计取舍（Design trade-offs）

> 提交要件要求给出「架构图 + 信任边界 + 关键设计取舍」。信任边界在
> [`architecture.md`](architecture.md)，这里是**取舍**——每条都写清「我们选了什么、
> 放弃了什么、代价是什么、哪条测试盯着我」。
>
> 这不是 ADR 全集（我们没有 13 条那样长的决策记录），而是**评审最该复核的六条**：
> 每一条都对应一次真实的失败或一次刻意的拒绝，不是事后追认的设计说明。

读法：**代价**一栏是重点。只有写清代价的取舍才可信——一个「没有任何代价」的决策，
通常只是还没想清楚。

## D1 · 评分卡由代码算，不让模型打分

| | |
|---|---|
| **决策** | `gtm_research` 的 Fit / Timing / Access / Intent 四维评分由 `scorecard.py` 按 `sample_docs/gtm/icp-targeting.md` §6 的既有条款算出，LLM 降级为叙述者 |
| **放弃** | 让 LLM 直接打分（更灵活，能吃下模糊、口语化的客户描述） |
| **理由** | 「可审计」与「模型打分」直接冲突：同一份客户资料两次运行给 86 和 72，销售无从复核，合规部门更拿不到证据。评分卡的每一分必须能指回具体条款（如「B 轮及以上 → 20–25」），否则它只是一句漂亮的意见 |
| **代价** | 条款之外的信号拿不到分；输入必须含结构化事实（行业 / 人数 / 融资轮次 / 月付笔数），纯描述性输入会落到「待补事实」而不是给个大概分 |
| **证据** | `test_gtm_scorecard.py` 56 断言：可复现性 4（同输入 5 次必同分）· 每档指回条款 12 · **红线优先于分数** 8 · **缺事实 ≠ 不追** 8 |

> 第 4 组是刻意加的：只测「分数对不对」的话，一个把所有不确定输入都判成「不追」的实现
> 也能满分——那是把谨慎伪装成安全。缺事实必须记 0 并标「需人工补充」，且明确区分
> 「事实齐全但确实低分 → 判断」与「事实不全导致低分 → 只是没问清楚」。

## D2 · 检索默认走词法（BM25 + TF-IDF），dense embedding 是开关不是默认

| | |
|---|---|
| **决策** | 默认纯词法检索；稠密向量做成开关（`USE_DENSE_EMBED=1` + `EMBED_MODEL`，见 `kb_qa.py` 配置） |
| **放弃** | 默认向量检索（同义改写召回更好，长尾问题更友好） |
| **理由** | ① **可复现**：CI 与评委本机不需要任何 embedding 服务或 key，十套 337 条断言在空环境里也能全绿；② **可控**：权限过滤必须在检索阶段生效（pre-retrieval ACL，OWASP LLM08），词法索引与 ACL 的组合行为更容易被断言钉住；③ **语料规模**：16 篇 / 96 分块，词法已足够，中英混排时中文单字 + 二字 bigram 的分词行为可预测 |
| **代价** | 同义改写只能靠 `QUERY_SYNONYMS` 兜底（只改查询侧，不动语料）；长查询里的专名与虚词会压低相关性分，语料越小越明显 |
| **证据** | 相关性门 0.17 由 27 组标注样本标定，三类完全分离（无关 ≤0.145 / 弱相关 ≤0.152 / 有答案 ≥0.244）；`test_relevance.py` 21 断言守住余量（无关最高 0.1492 < 0.17 < 命中最低 0.2464） |

## D3 · 语料里不存在的词（OOV）**必须**计入 BM25 上界

| | |
|---|---|
| **决策** | `BM25.self_ceiling()` 把查询自身当作一篇文档算上界时，df=0 的词照常累加 |
| **放弃** | 只累加语料中存在的词（看起来更「正确」：不存在的词凭什么贡献上界？） |
| **理由** | **实测反例**：10/15 改成只累加 df>0 的词后，「今天天气怎么样」这类**全 OOV** 提问的分数从 0.15 暴涨到 0.73——分母塌缩成只剩个别常见字，0.17 阈值彻底失效。换言之，「查询里全是语料中不存在的词」恰恰是「这个问题不该有答案」的最强信号，上界必须把它计入 |
| **代价** | 长查询里的专名 / 虚词会压低分数（「DIS-118 争议的处理结论是什么」低于「争议处理结论」），语料越小越明显 |
| **证据** | 该性质的注释直接写在 `kb_qa.py` 的 `self_ceiling()` 上方——**它是一次真实失败留下的**，不是设计说明；`test_relevance.py` 的标定会在误改时立刻崩 |

> 生产路径是加 cross-encoder 重排，而不是动上界本身。见 README「已知边界」。

## D4 · 盾牌靠规则与校验，不靠模型

| | |
|---|---|
| **决策** | 11 类标识用**校验**而非长度猜测来识别（卡号过 Luhn、IBAN 过 mod-97）；提示注入用短语与结构规则扫描 |
| **放弃** | 用 LLM（或小模型分类器）判断「这段是不是敏感信息 / 这行是不是指令」 |
| **理由** | ① 这道闸的**全部意义**就是「在内容进 LLM 之前拦住它」——扫描器本身不能再依赖一次 LLM 调用；② 规则可在 CI 里被**成对断言**对拍，模型的判断只能被「感觉对」地说服 |
| **代价** | 可被改写成不含扫描词表的注入绕过；人名检测只覆盖被标注 / 带称谓的人名，街道名不覆盖。剩余防线是「LLM 无写路径 + 答案复检 + 审计留痕」 |
| **证据** | `test_shield.py` 32 断言，含**反向断言**：「16 位但 Luhn 不过的流水号**不得**被掩码」「正常业务文本**不得**被误删」。只测「卡号被掩码」的话，一个把所有数字全糊掉的实现也能满分 |

## D5 · 演示语料 + 连接器插槽，而不是接真实平台

| | |
|---|---|
| **决策** | 语料是 16 篇本地 Markdown，来源平台徽章一律带 `·demo`，`/api/health` 返回 `demo_corpus: true`；连接器是统一 ingest 契约 + 平台常量表的插槽 |
| **放弃** | 接真实 Confluence / Jira / Drive 的 OAuth 与每问回源校验（同赛道有项目正是这么做的） |
| **理由** | 把有限的验证资源集中在**权限与审计的形式化不变量**上——那些能在 CI 里被 337 条断言反复证明；连接器实现只会被评委点一次。换成真实连接器时，每一道闸门、每一套测试、每一条不变量都不需要改动 |
| **代价** | 无法在真实平台权限模型上端到端验证，赛题第 2 项因此标为「**部分**」（过滤机制已实现且被测到 leak=0，但未在真平台验证过） |
| **证据** | README「赛题 7 项硬性要求 → 完成度」表 + [`requirements-map.md`](requirements-map.md)；「关于演示语料」一节明确写了这是**刻意的范围选择，不是未完成的掩饰** |

> 我们对这条的态度：宁可在 README 第一屏自己写出「部分」，也不让评委翻到代码才发现。
> 对持牌金融机构的评审而言，说清自己没做到什么，本身就是 Responsible AI 的一部分。

## D6 · 审计落在 SQLite 哈希链，不落外部日志服务

| | |
|---|---|
| **决策** | SQLite WAL 全量审计 + append-only 触发器（连 owner 的 UPDATE/DELETE 也拦）+ SHA-256 逐条哈希链，`POST /api/audit/verify` 一键重算 |
| **放弃** | 托管日志 / WORM 存储 / 外部 SIEM（更接近生产合规方案） |
| **理由** | 零外部依赖，评委可以**当场**点一下就看到「链完整 · N 条记录全部可验证」，而不是看一段「我们用了不可变存储」的声明 |
| **代价** | 单机；拿到 owner 登录的人理论上可以重写整条链——所以 verify 会返回链头哈希，**必须记在系统之外**（这条局限我们写在 README 里，没藏） |
| **证据** | `test_audit_chain.py` 6 断言：append-only 触发器拦截 UPDATE/DELETE + 篡改必被定位到行 + 旧库迁移回填 |

## 一条贯穿六者的原则

**能让确定性代码判定的，就不交给模型。** 权限、相关性、评分、脱敏、审计——全部在
确定性代码里，LLM 只在两处出现（子问题规划、答案合成），且**无任何写路径**。
这条原则的代价是灵活度（D1、D2 的代价栏都源于此），收益是每一条都能被断言钉住：
十套 337 条断言，全绿，无需任何 LLM key。
